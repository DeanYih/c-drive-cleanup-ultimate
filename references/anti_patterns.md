# 反面模式清单 —— 清理类工具的十种常见坑

> 用法：Stage 2 出报告前扫一眼；写任何面向用户的文案时对照本文。
> 每条分三段：**现象**（这类设计长什么样）、**危害**（为什么不能这么做）、
> **本技能的反向做法**（对应哪条红线 / 哪个脚本）。

---

## 1. 默认永久删除，却把「不可恢复」藏在二次确认里

**现象**：主界面话术是「已勾选 N 项，一键清理」+「成功释放 X 空间」；只有点进二次确认弹窗
才看到「清理后不可恢复」。回收站只是众多路径里最不起眼的一条。

**危害**：用户以为"清垃圾"天然可逆，实际一键之后原件没了。这么设计的动机通常是
"真删才能看到空间数字上涨"（送进回收站空间并不释放），**是转化率驱动，不是用户利益驱动**。

**本技能的反向做法**（SKILL.md 红线 3）：
- 默认走 `shell_delete.py`（Shell API + `FOF_ALLOWUNDO`）→ 进回收站，可恢复；
- 只有「纯缓存且用户明确同意彻底删」才用 `python -S` 真删；
- 报告里**同时给两个数字**：`进入回收站（可恢复）` 与 `实际释放空间`，并解释为什么两者不等。

---

## 2. 把「磁盘占用」偷换成「性能问题」

**现象**：文案围绕"越久不清越卡""清完立刻变快"展开，把「垃圾文件多」与「系统卡顿」
强行绑定，并给出无条件的速度承诺。

| 典型文案 | 手法 |
|---|---|
| 「已经 N 年没清理了，电脑快被挤爆了」 | 极端化 + 拟人恐吓 |
| 「N 天没清理，电脑越来越卡」 | 因果强行绑定（垃圾多少 ≠ 卡顿） |
| 「马上提升系统运行速度」 | 无条件承诺 |
| 「垃圾过多让电脑变卡慢」 | 把"文件多"直接等同"性能差" |
| 「定期清理，电脑更轻快」 | 循环暗示 |

**危害**：用户清完 2 GB 发现还是卡，信任崩塌；还催生"清理强迫症"——
磁盘 80% 空闲也要每天清一遍。

**本技能的反向做法**：
- 报告**只给事实与因果说明**：多少字节、哪些类别、清掉后**空间**会涨多少（不承诺提速）；
- 明确写"清理不影响运行速度，卡顿请查启动项 / 内存 / 磁盘健康"；
- Stage 2 必须给**释放量占总容量比例**（如 1 GB / 220 GB），主动管理预期。

---

## 3. 任务结束后弹评价 / 导流

**现象**：每个功能模块各埋一条评价引导，用完即弹，把人导去应用商店评分；同一套弹窗
框架顺带承载广告位。

**危害**：工具变成流量入口，打断用户正在做的事，且用户的真实反馈被"求好评"污染。

**本技能的反向做法**：不评估、不导流、不弹窗。任务结束就结束，只交付报告。

---

## 4. 把真正省事的能力锁进付费档

**现象**：手动一键清理免费；**定时自动清理**和**大文件搬家**这两件真正省事的事标成付费特权。
免费版实际交付的是"手动点一下 + 看广告位"。

**危害**：把「减少用户操作」当作商品，等于故意把产品做得难用。

**本技能的反向做法**：
- `gen_clean_task.py` —— 定时清理，免费，生成 Task Scheduler XML（且**不自动注册**，控制权留给用户）；
- `migrate_with_junction.py` —— 搬家，免费，且有源目录留底 + `--rollback` 一键还原，
  并带 `--audit` 台账核对（`OK` / `BROKEN` / `RETARGET` / `MISSING`）；
- 不做任何功能门禁。

---

## 5. 规则静默热更新，用户无法审查

**现象**：客户端定期从远端拉规则包，落到本地二进制配置里，**不发版、不通知、不可回滚**。
今天能清的目录，明天可能被划进"可清理项"。

**危害**：用户对"会被删什么"没有稳定预期；规则更新可以被用来悄悄扩权
（例如把「应用下载目录」新增为可清项）。

**本技能的反向做法**：
- `references/risk_rules.json` 与 `targets_catalog.md` 都是**明文、可读、可 diff**；
- 规则变更必须写进报告尾部「本次规则版本」；
- 用户可用 `--rules` 指定自己的规则文件，覆盖内置；
- 内置规则变更随技能版本号走，可回滚。

---

## 6. 系统注入：右键菜单 / 桌面快捷方式 / 任务栏工具栏

**现象**：在「我的电脑」和驱动器右键里插入自建菜单项，静默创建桌面快捷方式，
甚至挂一个任务栏工具栏；顺手装一个守护进程保证这些入口删了还能被重建。

**危害**：用户删掉的入口会被重建；右键菜单层层嵌套；**这些注入本身就是它宣称要清理的"垃圾"**。

**本技能的反向做法**：
- **零系统注入**：不写 Shell 扩展、不建快捷方式、不加计划任务（除非用户显式要求，
  且脚本只生成不注册）；
- 只操作文件与配置，退出即无痕；
- 若用户要"常用入口"，只建议系统自带方式（固定到开始菜单），不代劳。

---

## 7. 扫描硬截断且不告知

**现象**：配置里硬编码单次扫描上限（如最多 30000 个文件、单次扫描最多 300 秒），
超限直接停，界面上没有任何"未扫完"的提示，却照常给出一个总数。

**危害**：一台有 80 万个文件的机器，只看了 3.75% 就敢报"共 12.4 GB 垃圾"。
用户以为扫完了，实际大量可清项根本没被发现 → **系统性低估**。
（本技能自己也踩过同一个坑：17.2 GB 的 WinSxS 因遍历截断被误报成 5.16 GB，见 pitfalls。）

**本技能的反向做法**（红线 11）：
- `scan_safe_targets.py` **无上限遍历**；
- 任何必须设上限的场景（如 `scan_tiers.py --max-files`），输出里**强制带**
  `"truncated": true` + `"scanned_files"` + `"note": "已截断，结论为下限"`；
- 报告头部永远先写"本次扫描覆盖 X 个文件 / Y GB，是否完整"。

---

## 8. 「采集」类动作默认开启

**现象**：某功能（如弹窗拦截）运行时，顺手以一定概率截屏采集，用于优化自己的规则；
配置项里 `Collect=1` 与 `ScreenShot=1` 是默认值，界面上没有开关也没有说明。

**危害**：屏幕内容包含聊天、邮件、密码管理器界面。抽样截屏在隐私上是**不可接受的默认值**，
哪怕概率只有 20%。

**本技能的反向做法**：本技能不做弹窗拦截，也不做任何"采集"类动作。
若用户需要拦截，推荐系统自带 / 可信开源工具，并明确提示截图类采集的风险。

---

## 9. 埋点上报与文件上传接口

**现象**：每个功能模块的状态与结果都上报；客户端里有独立的文件上传接口；
本地落一个事件队列，文件名本身就是事件名，另有设备指纹文件与累计上报计数。

**危害**：扫描结果（文件名、路径）具备强辨识性，一旦上传即等同于**目录清单外泄**——
里面往往带着客户名、项目名、私人照片的目录结构。

**本技能的反向做法**（红线 12，硬性）：
- `scripts/` 下**所有脚本零网络调用**（无 `requests` / `urllib` / `socket` / `http`）；
- 扫描产物只写本地 `outputs/`，报告里的用户名默认打码为 `%USERPROFILE%`；
- 分享报告给他人前，提示先跑一次脱敏。

---

## 10. 一句话总结

> 把用户当成"转化目标"，还是当成"机器的临时托管人"——这是分野所在。

差异不在技术，在**默认值**：
- 默认永久删 / 默认可恢复；
- 默认上报 / 默认零联网；
- 默认注入系统 / 默认不落痕；
- 默认把能力锁起来 / 默认全给。
